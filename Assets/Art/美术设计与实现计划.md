# Project_Chaos 美术设计与实现计划

日期：2026-11-05。状态：基于现有工程核查形成的第一版建议，供本会话后续美术工作使用。画风、制作数量、时间参数与性能指标均为建议或待实测目标，不表示已获用户定稿或已实现。

## 1. 已核实的工程基线

| 范围 | 当前事实 | 对美术的影响 |
| --- | --- | --- |
| 平台与玩法 | 策划面向 Windows PC；实体村庄经营、世界地图管理、2D 横板探索战斗；派遣至多四名门客 | 场景需要兼顾经营空间识别、四人队伍辨识与战斗读图 |
| 正式流程 | EnterScene → MainScene 村庄 → LoadingScene → WorldScene，存在世界地图子界面 | 美术验收需要覆盖场景切换、返回与对象清理 |
| 引擎与渲染 | Unity 2022.3.57f1c2；Linear；已安装 URP 14.0.11，但实时查询的 default/current/quality RenderPipeline 都为空，实际是 Built-in | 不能把 URP 配置文件存在等同于已启用 URP |
| 角色 | Spine 数据声明 3.8；运行时兼容声明为 3.8；现有 citizen_001 只有 Idle_Normal、Run_Normal、Walk_Normal | 优先补充动作，并固定编辑器导出与运行时版本组合 |

| 镜头与昼夜 | Cinemachine 2.10.3；GameplayCameraRig 统一控制；DayNightSkyRenderer 使用 Built-in CameraEvent 和 CommandBuffer 合成天空、世界着色 | 新特效服从单一镜头输出，URP 迁移需重做该渲染接入 |
| 地形 | NaturalMapAssembler 依据地形计划选 top/fill，拼接手工结构，合成 Tilemap 碰撞 | 需要补充邻接边缘的视觉选择；美术轮廓必须对齐可站立面 |
| UI | uGUI + TMP + MVP；Art/UI 已有切图规范，素材设计 2800×1575，预制体参考布局 1920×1080 | 保持既有布局逻辑，以九宫格和统一状态皮肤改善外观 |

## 2. 建议画面方向

采用“秦汉题材的风格化手绘 2D”：清楚的外轮廓、受控的平面设色、局部笔触和材质颗粒、适量的分层纵深。先以现有镜头中的实际显示尺寸判断细节，角色、背景、地图和 UI 共用色彩与装饰语汇。

| 场合 | 构图与材质 | 动态重点 |
| --- | --- | --- |
| 村庄 | 土木、夯土、织物、黑瓦；生活区域偏暖，建筑职能靠形体和招牌可辨 | 烟、布幡、劳作、行走、灯火 |
| 局内地表 | 远景简化、可行走面清楚；土石植被使用同一绘制尺度 | 风、草木、尘土、角色剪影 |
| 洞穴与遗构 | 冷灰、赭石、石青；收敛背景细节，保持墙地交界与出口可见 | 水滴、薄雾、局部火光、危险提示 |
| 边缘空间异常 | 在基础环境中重复使用一套有规则的非自然形状、光纹和运动方式 | 传送、空间扰动、不同文明的视觉标记；文明语汇后续分别设计 |
| 世界地图 | 保持现有纸本舆图；地点、资源、任务图标按缩放层级显示 | 选中、路径、任务变化，动画不干扰地名与疆域 |
| 界面 | 深墨、纸色、适量金属与朱色；正文对比稳定 | 焦点、按下、禁用、解锁、结果反馈 |

起始色板沿用现有说明中的墨 #2A2420、朱砂 #B03A2C、赭石 #8A5A3A、石青 #3E6E7A、石绿 #6B8A5A、金 #C9A227、纸 #E7DDB4。它是制作锚点，最终颜色须在 Linear 工作流和昼夜合成后评审。

角色建议保持可辨的成人比例，适当强化头、手、武器和服装块面。历史服饰与建筑细节按具体年代另做参考板；当前已有的地图装饰只作为风格参考，不能直接视为全时期的考据结论。

第一批评审交付：同一画风下的一张村庄关键帧、一张地表/洞穴关键帧、一张角色与 UI 同屏图。必须包含最终镜头尺度和 HUD，原画局部放大图不能单独作为定稿依据。

## 3. 技术栈与架构接入

| 层 | 首轮建议 | 实施边界 |
| --- | --- | --- |
| 渲染 | 沿用 Built-in + ShaderLab/HLSL，保留现有昼夜入口 | 先交付样板，再决定是否迁移 URP 2D Renderer |
| 人物 | Spine 分层原画、骨骼与适量网格变形；Skin/Attachment 复用 | 先验证一个正式角色及其 UI 预览，再扩展同骨架变体；不同体型单独评估 |
| 环境 | Tilemap 负责连续地形；Sprite/Prefab 负责建筑、岩石、植被；分层背景形成纵深 | 视觉装配读取地形计划，不由贴图透明度决定碰撞与通路 |
| 特效 | Unity Particle System、短序列帧和少量程序材质 | 高频命中特效走可复用对象；先核对现有 PoolManager 的清理契约再接入 |
| UI | 继续使用 uGUI、TMP、现有显隐动画体系 | View 播放动画，Presenter/Model 维持业务权威；关闭动画不阻塞业务和清理 |
| 资源 | 首轮复用 Resources/ResManager 与显式引用 | 不为换皮同时引入 Addressables 或改变存档结构；扩量后按实测加载成本评估 |
| 制作源 | 分层 PSD 或现有绘画工具源文件、Spine 工程、地图/UI 的现有矢量源 | 工具选择服从团队已有环境；保留可编辑源、导出规则和导入预设 |

URP 只在目标画面确实需要动态 2D 光照、法线和更统一的屏幕效果时进入验证。独立验证须覆盖 Spine 3.8 的可用 Shader 组合、Tilemap、SkeletonGraphic、天空与昼夜、粒子、遮罩、Linear 透明边缘和目标机帧时间。仅安装 URP 或套用最新版 Spine 扩展都不足以证明兼容。

现有可复用表现入口：RunCharacterPresentation（职业、头像、预览 Skin）、RunContentVisualSettings（NPC、宝箱、采集物）、FamilyTreeVisuals、DispatchVisuals。VillageVisuals 当前仍通过矩形、标签与角色外观副本构造内容；正式村庄建筑需要建立独立外观 Prefab/配置，保留交互身份和业务入口。

建议新增职责为角色动作适配、场景主题数据、环境装饰装配、特效播放与清理。具体类名在实现时确定，避免提前创建空框架。表现代码不写生成配置类、奖励规则或真实玩家存档。

## 4. 动作与流畅性

先补完整状态，再调整采样与混合。首名正式门客至少包括待机、走、跑、起跳、上升/下落、落地、普通攻击、受击、倒地与恢复；交互/道具动作根据首轮样板实际出现的内容补充。首种敌人至少包括待机、移动、攻击前摇、攻击、恢复、受击、死亡。

| 维度 | 建议与验收 |
| --- | --- |
| 游戏显示 | 以目标 PC 的 1080p 稳定 60fps 为首轮目标，帧预算约 16.67ms；目标硬件尚待确定，不承诺已达标 |
| 骨骼动画 | 动作可用 24/30fps 时间标尺制作，运行时连续插值；关键姿势、轮廓、重心比堆关键帧更优先 |
| 序列帧 | 烟火、刀光、冲击等根据效果用约 12–24fps 起测；移动位置和透明度仍按运行时间更新 |
| 物理与镜头 | 当前 Fixed Timestep 为 0.02 秒，即 50Hz；Player 预制体启用插值，Ally 未启用，村庄动态创建角色也需核查。先测试插值与 Cinemachine 跟随一致性，再决定是否改物理步长 |
| 混合 | 现有 SkeletonData defaultMix=0.2 秒；走跑可从 0.08–0.15 秒试起，攻击/受击采用更短且明确的切换，数值通过实录比较确定 |
| 跑步 | 周期与世界位移匹配；脚接地阶段尽量不滑动；视觉位移不移动碰撞根节点 |
| 图层 | 底层移动，上层受控的攻击/交互覆盖；同一动作不由多个组件竞争写入 |

玩家当前 attackCooldown=0.35 秒且立即造成判定。正式攻击动画必须先对齐该行为；若引入可见前摇并延后判定，应单独明确战斗时序改动，使用同一动作参数驱动判定与动画。不能在美术替换中悄悄增加输入延迟，也不能让刀光或动画播放完成决定伤害是否发生。

命中反馈组合建议：攻击姿势与轨迹、接触特效、目标短暂闪色、伤害数字、已有 Cinemachine Impulse；屏幕抖动服从现有开关与强度设置。首轮不增加全局 Time.timeScale 顿帧，因为暂停、UI 和四人队伍都受其影响；确有需要再设计专门时钟。

## 5. 地形与视觉语言

地形从 top/fill 扩展为可验证的视觉邻接规则：顶面、底面、左右边、内外角、孤立块、平台端头以及土/石/人工材料交界。RunMapChunkTiles 目前字段类型为 Tile，不能假定把 RuleTile 资源拖入就可工作；需要有意识地扩展主题类型或按邻接掩码挑选 Tile。选择哪种实现，以同种子样板和装配耗时比较决定。

碰撞继续来自最终地形计划。可站立边缘要与碰撞吻合，装饰草、树枝和岩石突出部分单独处理；前景不能遮蔽敌人前摇和跳跃落点。重复纹理使用稳定种子的变体，重新加载同种子保持一致；不靠随机装饰遮盖拼接错误。

建议的排序职责为天空、远景、环境背层、地形、角色、交互/战斗特效、近景、HUD。具体 Sorting Layer 与 order 区间在实现前盘点现有值；不能直接把示意职责作为一套全局数值覆盖原配置。沿用唯一 GameplayCameraRig 输出链路。

视觉语义先冻结用途，再绘制资源：

- 受控门客用脚下标记、头像焦点与轮廓区分，队友不与受控者完全同样高亮。
- 敌方前摇用明确动作、方向或区域形状表达，颜色作辅助；不能只靠红绿区分阵营。
- 可交互物用轮廓/小型标记与按键提示；可采集、已采集、可开启、已开启有不同形态。
- 危险提示优先于掉落提示；高亮色只占较小面积，多个队友同时攻击仍能看清落点。
- 世界地图势力色专用于政治归属，地点选中、经营权限和任务状态使用额外图标/线型，避免改变历史疆域的含义。
- 家族树锁定、可解锁、已解锁和里程碑采用形状、纹理与明度共同区分；手柄焦点须始终清楚。

## 6. Shader 编写顺序

| 阶段 | 材质或效果 | 验证重点 |
| --- | --- | --- |
| P0 | Spine 兼容的闪色、淡出、可选细轮廓 | 匹配现有 PMA/straight-alpha 数据；世界角色与 SkeletonGraphic 分开处理；透明边无黑白边 |
| P0 | 保留并调校 DayNightSky2D 的环境色、天气色与洞穴遮挡 | 夜间可站立面与敌人仍可辨；HUD 不被世界调色压暗；洞口切换自然 |
| P1 | 植被顶点摆动、布幡、低速水面 | 根部固定；随机相位稳定；噪声/UV 不在移动镜头下游移 |
| P1 | 雾层、尘土、火光、传送光纹 | 透明过绘、队伍遮挡、特效生命周期、昼夜下的辨识 |
| P2 | 纸纹、轻量色彩统一、局部空间扭曲 | 小字清晰；全屏效果按 GPU 成本逐个加入；有质量开关 |

先用贴图表现线条、块面和笔触，再以 Shader 增加运动和反馈。共享 Shader 配合少量材质预设；实例差异使用顶点色或已验证的 Spine 扩展接口。不要假定 Spine 存在 _Color 属性，也不要直接每帧改 MeshRenderer 材质数组；它可能被 SkeletonRenderer 重写。

UI 图标的 alphaIsTransparency 导入规则不能套到全部 Spine 图集。当前角色素材为低分辨率图集，meta 里还有 Point、mipmap 与 sRGB 等既有配置；正式素材需要重新验证整套导出/导入组合，不把旧设置继承为默认正确。

首轮只维护实际运行管线的实现。Shader Graph 作为 URP 验证通过后的选项，不在 Built-in 首轮计划中假定可直接替换现有 Shader。

## 7. 素材规格与生产

统一世界尺寸、脚底枢轴、光照方向、画面内笔触尺度，按资源种类设置 PPU，不把全项目固定为同一个数值。建议环境光方向沿用既有地图说明的左上；镜像部件要检查光照、文字和服饰不对称信息。

现有镜头说明中局内 orthographicSize=6、村庄=8；若占满 1080 像素高视口，约为 90 和 67.5 像素/世界单位。1.7 单位高的人物约显示为 153 或 115 像素高。正式角色的细节和描线须在这个尺度评审，头像与面板放大预览可另备清晰素材。

建议首轮角色绘制高度从约 512 像素起测；地形在 1 单位网格下从 128 像素/格起测，近景装饰可提高密度。这些不是全资产硬指标，需同时验证 1366×768、1920×1080、2560×1440 与实际镜头缩放。UI 继续遵守 Art/UI/README.md 的九宫格和参考布局规则。

制作顺序：参考板与线稿 → 同屏关键帧 → 分层与绑定 → 动作 → 导出与导入预设 → Prefab/表现配置接线 → 可操作验收。每批交付保留源文件、导出文件、可追溯名称、素材来源与授权记录。新增类或工具实现时应用项目的中文注释约定。

图集按实际同屏和加载生命周期分组：角色/角色族、环境主题、UI 公共件、地图图标。Spine 保留自己的 atlas 管线；不为“统一图集”把所有角色拆件和界面混进一张大图。是否合批和材质切换次数以 Frame Debugger/Profiler 为准。

## 8. 分阶段交付与验收

| 阶段 | 具体交付 | 完成条件 |
| --- | --- | --- |
| A 风格与尺度 | 三张同屏关键帧、色板、角色比例与边缘规范 | 村庄/地表/洞穴的风格一致；四人队伍、敌人、可站立面和 HUD 在实际尺寸下可读 |
| B 可操作样板 | 一名正式门客、一种敌人、村庄街段、地表到洞穴的过渡、宝箱或采集点、战斗 HUD | 从村庄进入样板并返回；走跑跳、攻击、受击、倒地与交互完整；透明与排序正常 |
| C 动作与反馈 | 同一动作规格覆盖受控者和队友；核心 Shader 与命中特效 | 四人同时移动/攻击无明显脚滑、动画抢写、轮廓丢失；判定时刻与画面一致；暂停与切场景正确清理 |
| D 环境扩展 | 地表、地下、人工结构的视觉邻接规则和主题变体 | 多个种子无明显边缝；镜像结构、洞口、平台端头和材料交界正确；同种子几何与导航保持既有契约 |
| E 界面与量产 | 派遣、家族树、市场、背包等统一皮肤；角色与建筑变体规范 | 键鼠/手柄焦点、中文长文、多种分辨率正常；资源不靠重复复制扩量 |
| F 性能收口 | 目标硬件与最坏同屏场景的独立构建记录 | 报告 CPU/GPU 帧时间、P95/P99、GC、显存、加载峰值和材质切换；质量档可回退 |

B 的建议场景长度为约 30–60 秒可反复操作的内容，并非新玩法时长要求。首轮先完成第一时代的一套可复制规格，再用材质、服装、建筑状态和叙事标记扩展时代变化。

所有帧率目标均以明确硬件、分辨率与画质的独立构建实测；不以编辑器平均 FPS 或一张截图作验收。正常可操作期间目标维持 16.67ms 预算，地图生成/切换另记录加载耗时和峰值卡顿。首轮性能场景为四名门客加实测的最高可达敌人数及叠加特效，数量以当前玩法为准。
